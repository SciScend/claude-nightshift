claude-nightshift · Pro & Max plans

Working the night shift without spending the week

Run one Claude Code task for hours unattended. Every time the 5-hour session limit lands, nightshift waits out the window and resumes — so the session gaps you'd otherwise sleep through get used — while a window budget keeps a single task from eating your whole weekly pool.

Quick start

claude-nightshift "fix all the failing tests"

Runs the task, waits out every 5-hour limit, stops when weekly usage reaches 70%.

For a long unattended stretch — the case this is built for:

claude-nightshift -w auto --horizon 20h "migrate the API layer to v2"

Now it also refuses to spend more of the week than a 20-hour stretch is entitled to.

The two limits, and which one bites

WindowWhat it isWhat nightshift does
5-hour Resets every 5 hours, around the clock Waits it out and resumes. This is the loop.
7-day Your weekly pool Decides whether there should be another session at all.

Inside one stretch the 5-hour window decides how long you work. The weekly pool decides how many stretches you get this week. Different questions, so they get different controls.

Controlling weekly spend

-t, --threshold — the wall

claude-nightshift -t 85 "long refactor"

Never start a session at or above this weekly percentage. Default 70. An absolute ceiling — nothing below can raise it, and it's the right tool for "always keep 30% in reserve for my interactive work."

On its own it answers "am I out of weekly budget?" — but not "should this one task be allowed to spend what's left?" That second question is what everything below is for.

-w N — the boring, predictable cap

claude-nightshift -w 2 "big refactor"

At most two 5-hour windows, then stop, even if the threshold is nowhere near. Use it when you know what a task is worth.

-w auto — spread what's left over the time that's left

claude-nightshift -w auto --horizon 20h "big refactor"

This run is entitled to the share of the remaining pool that its horizon is of the time before the weekly window resets.

--horizon — the one input only you know

How long you're actually leaving it unattended: 20h, 90m, 2d, or a bare number meaning hours. Default 12h. Only -w auto reads it.

The denominator is wall-clock time to the reset, not time you're available. With 90h before the reset but only two 20h stretches in it, auto under-allocates. That errs safe — the slack stays there for your daytime work — but it's why auto can feel stingy. Raise --horizon, or use an explicit -w N, to lean the other way.

--no-overshoot — don't start what you can't finish

Weekly usage moves in lumps of roughly one window at a time, so a plain threshold can only notice you crossed it after a session already did. This checks first: if current + one window lands past the ceiling, it declines to start.

claude-nightshift -t 70 --no-overshoot "long task"

-w switches this on for you. The flag alone gives it to you without a window cap.

--min-window-left — don't start in a window that's already gone

The threshold and the window budget both answer weekly questions. Neither looks at the 5-hour window the next session would actually run in.

Start nine minutes before a 5-hour reset and you get a session that dies on the limit having done nothing — and that stub used to be charged to the window budget anyway. A -w auto --horizon 10h run that had budgeted exactly one window would end after five minutes, having produced nothing.

So the 5-hour window is now checked before each session too. If less than --min-window-left percent of it is left, nightshift waits for the reset instead of spending a budgeted window on it:

5-hour window is 100% spent (0% left, need 5%). Waiting for it to reset at
2026-09-04 15:40:00 (~9.5 minutes) rather than spending a window on it.

A wait is not a retry and not a window — it costs nothing but time. Three consecutive waits that fail to clear the window mean something is wrong with the reading, so the session starts anyway rather than looping.

--min-window-left 0 disables it. An unreadable 5-hour figure, or one with no credible reset time to wait for, always reads as ready: this gate can only block on a number it actually has.

A stub is not a window for accounting either. A session that hits the limit within 15 minutes ran in a window that was already spent, so it's neither counted against -w nor used as a sample of what a window costs. It does still spend real weekly budget, so a tight run ceiling can still stop the run — the other reason to leave this gate on.

The arithmetic, worked

You've used 22% of the week. The pool resets in 3 days 18 hours. You're leaving the machine for 20 hours.

Given

Weekly used
22.0%
Weekly left
78.0%
Until reset
90h
Horizon
20h
Per window
~8%
allowance= 78.0% × 20/90 =17.3%
ceiling= 22.0% + 17.3% =39.3%
windows= 17.3% ÷ 8% =2

A 20-hour stretch could hold four 5-hour windows. auto deliberately takes two and leaves the rest of the week alone. That trade is the whole point — if you'd rather have all four tonight, say -w 4, or drop -w entirely.

Two properties worth knowing

It never quite empties the pool. Each run takes a share of what remains, so the remainder decays but never reaches zero. Slight systematic under-use — the price of never being caught short.

The last day is generous. As the reset approaches, horizon ÷ time_to_reset approaches 1, so the allowance approaches everything left. Use-it-or-lose-it, automatically. Expect the first day of a weekly window to feel much tighter than the last.

Window cost is measured, not guessed

The budget needs one number: what a full 5-hour window costs in weekly percent. Nightshift reads the weekly figure at the gate, then again from the session's last rate-limit event. The difference is the real cost — and it's free, because both figures are already in Claude's output stream.

The median of the last 20 samples lives in ~/.claude/nightshift-state.json, so from your second run onward the arithmetic is calibrated to your actual workload instead of an assumption. Until then a conservative 8% placeholder is used, and the log says so:

Window cost   : ~8.0% of weekly (estimated, no samples yet)
...
[budget] window 1 cost 6.4% of the weekly pool (estimate now 6.4% from 1 sample(s))

Samples that can't be real are discarded — a negative delta means the weekly window reset mid-run. Delete the state file to start over.

Reading the log

Starting claude-nightshift
  Command       : claude --model opus --output-format stream-json --verbose -p ...
  Weekly gate   : start a session only below 70.0%
  Window budget : auto, over a 20h horizon
  Window cost   : ~6.4% of weekly (measured)
  Max retries   : 10
  Compress after: 3 resumes
  Auto budget   : 17.3% of the weekly pool (78.0% left, 20h horizon of 90h to reset)
  Window budget : 2 × 5h window(s) at ~6.4%/window (measured)
  Run ceiling   : stop before 7-day usage reaches 39.3%
Gate open: 7-day usage 22.0%, run ceiling 39.3%, window 1/2

The first Window budget line is what you asked for; the second is what it worked out to once real usage was read. Run ceiling is the number actually enforced — always the lower of your threshold and the auto allowance.

Why it stopped

MessageKindMeaning
window budget spent — 2 of 2 five-hour window(s) used budget Your -w count is exhausted.
7-day usage X% is at or above the run ceiling Y% budget This run's auto allowance is gone. The week isn't — a new run gets a fresh share.
7-day usage X% is at or above the threshold Y% wall The real limit. Nothing starts until the weekly window resets.
another window would reach ~X%, past the ceiling Y% budget --no-overshoot declined to start a window that wouldn't fit.
5-hour window is X% spent … Waiting for it to reset wait Not a stop. The next window is worth more than the minutes left in this one.
weekly usage could not be determined unknown Couldn't read usage, so it stopped rather than run blind. --allow-unknown-usage flips this.

Exit code is 0 only when the task actually completed. The other codes say why the run stopped:

Exit codeMeaning
0The task completed.
1Failed: Claude error, retries exhausted, or usage unreadable.
2Usage error: bad arguments, unreadable or empty --task-file.
3Weekly limit: --threshold reached. Nothing else should start this week.
4Run budget spent (-w N or -w auto), task not finished. Run it again later.
130Interrupted.

Resuming, and how context survives

On each limit hit nightshift resumes automatically. The first --compress-after resumes (default 3) continue the real conversation by session id, carrying full history. After that it starts fresh sessions seeded with the original task plus a progress summary Claude writes to .nightshift-status.md before each session ends — which keeps context from growing without bound across a long night.

claude-nightshift --compress-after 2 "very large refactor"

Commit .nightshift-status.md or add it to .gitignore. It's the handoff between sessions and gets rewritten constantly.

Model and effort

claude-nightshift -m opus -e medium "long refactor"

-e/--effort takes low|medium|high|xhigh|max. Lower effort spends fewer thinking tokens, so more work fits inside one 5-hour window — often a better trade than a bigger budget.

Bounded sessions

claude-nightshift --max-turns 50 "fix all lint errors"

Hitting the turn cap ends the session and nightshift resumes; it isn't an error. Turn-capped sessions do not count against -w, because they don't consume a whole 5-hour window.

Full control

claude-nightshift -w auto -- claude -p "task" --model opus --allowedTools Edit,Write

Everything after -- goes to claude verbatim; nightshift only adds --dangerously-skip-permissions and the stream format.

--hard-stop is off for a reason. By default the threshold is a gate checked before a session starts, and a session already running always finishes. --hard-stop restores the old behaviour of polling and killing mid-session — which loses unsaved work and stops the status file being written, breaking the compressed-resume handoff.

Where the numbers come from

In priority order. None of these spend tokens.

  1. The rate_limit_event in Claude's own output stream — free, already there, carries both windows and the exact reset time.
  2. api.anthropic.com/api/oauth/usage — one ~0.5s request using the OAuth token Claude Code keeps in ~/.claude/.credentials.json. The same endpoint /usage uses.
  3. cclimits --claude --json — fallback only, if both above fail.

A typical overnight run makes one request at startup and one after each 5-hour wait. Everything else is read out of the stream.

Recipes

# Overnight, unattended, don't blow the week
claude-nightshift -w auto --horizon 10h "task"

# Long weekend stretch, generous
claude-nightshift -w auto --horizon 20h -t 85 "task"

# Exactly two windows, no arithmetic
claude-nightshift -w 2 "task"

# Old behaviour, plus don't overshoot the wall
claude-nightshift -t 70 --no-overshoot "task"

# Everything you've got before the weekly reset
claude-nightshift -t 95 "task"

# Cheap and bounded, for something exploratory
claude-nightshift -m haiku -e low --max-turns 30 -w 1 "task"
